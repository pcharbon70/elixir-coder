# Training an Elixir LLM to Follow OTP Supervision Failure Policy

## Executive summary

This document defines a concrete policy task for Elixir code generation:

- In supervised worker internals, process crashes are acceptable when they represent invariant violations ("let it crash").
- At system boundaries (user input, HTTP, external APIs, serialization, database edge cases), expected failures should be handled explicitly.

The goal is to prevent two common errors:

1. **Over-defensive internal code** (`try/rescue/catch` everywhere inside OTP workers).
2. **Under-defensive boundary code** (propagating avoidable runtime exceptions to callers).

To teach this reliably, treat policy as an explicit multi-task objective, not just prompt wording.

---

## 1. Policy definition (what behavior we want)

### 1.1 Core policy

For generated Elixir code, classify logic into two contexts:

- `:supervised_internal`
  - Code executing inside supervised OTP worker callbacks or internal workflow steps.
  - Preferred behavior: crash on impossible internal state, allow supervisor restart semantics to recover.
  - Avoid broad rescue wrappers that hide bugs.

- `:boundary_handling`
  - Code handling untrusted input or integration boundaries.
  - Preferred behavior: return explicit errors or safe fallbacks for expected failures.
  - Avoid leaking exceptions that should be converted into domain errors.

### 1.2 Practical interpretation

"Let it crash" does not mean "never handle errors." It means:

- Handle **expected** failures at boundaries.
- Do not hide **unexpected invariant violations** inside worker internals.
- Use supervision strategy as the recovery mechanism when appropriate.

---

## 2. What is a policy task during training?

A policy task is a supervised objective that teaches the model "how to behave" under a specific operational doctrine, separate from pure next-token accuracy.

For this project, a policy task should answer:

1. Which context am I in (`:supervised_internal` vs `:boundary_handling`)?
2. Which failure behavior is idiomatic in this context?
3. Is this candidate implementation compliant with policy?

### 2.1 Why policy tasks matter

Language-model loss alone rewards statistically likely code. In mixed corpora, this often yields inconsistent error handling style. A policy task gives direct training signal about correctness of *behavioral posture*, not just syntax.

---

## 3. Data model for OTP failure policy

Each training sample should include explicit policy metadata:

```json
{
  "id": "sample-001",
  "prompt": "Implement GenServer handle_call for processing order transitions",
  "code": "def handle_call(...",
  "policy_context": "supervised_internal",
  "failure_policy": "let_it_crash",
  "restart_strategy": "permanent",
  "boundary_type": null,
  "policy_label": "compliant"
}
```

### 3.1 Required fields

- `policy_context`: `supervised_internal | boundary_handling | mixed`
- `failure_policy`: `let_it_crash | handle_expected_errors | hybrid`
- `policy_label`: `compliant | non_compliant`
- `non_compliance_reason` (optional): `broad_rescue_internal`, `missing_boundary_validation`, `swallowed_exception`, `unsafe_raise_boundary`

### 3.2 Provenance fields (recommended)

- `otp_component`: `genserver | supervisor | task | agent | plain_module`
- `callback_name`: `init | handle_call | handle_cast | handle_info | terminate | ...`
- `source_origin`: `hex | github | synthetic`

## 5. Dataset construction strategy

### 5.1 Positive examples

- OTP internals that do not use blanket rescue.
- Internal callbacks that assert invariants and rely on supervisor restart on failure.
- Boundary modules/controllers/plugs that transform predictable failures into `{:error, reason}` style outputs.

### 5.2 Negative examples

- Internal callbacks wrapped in broad `try/rescue` without selective, expected-error rationale.
- Boundary code that uses bang functions or raises on user-driven validation failures.
- Catch-all rescues that swallow exceptions and continue with invalid state.

### 5.3 Contrastive pair generation

Generate policy contrastive pairs from a compliant seed:

- Pair A (positive): callback without broad rescue.
- Pair B (negative): same logic wrapped in blanket rescue.

And inverse for boundaries:

- Pair A (positive): explicit validation/error tuple.
- Pair B (negative): raw exception flow for expected input faults.

---

## 6. Training design: how policy tasks work in practice

Use three complementary objectives.

### 6.1 Policy context classification head

Predict `policy_context` from prompt + code context.

- Loss: cross-entropy.
- Benefit: model learns to distinguish internal OTP callback logic from boundary handling code.

### 6.2 Policy compliance head

Predict `compliant` vs `non_compliant`.

- Loss: binary cross-entropy.
- Benefit: direct signal against over-defensive internal patterns.

### 6.3 Preference/contrastive objective

For paired samples `(compliant, non_compliant)`:

- Use InfoNCE or pairwise ranking loss to prefer compliant variant embeddings.
- Benefit: stronger behavioral separation than classification alone.

### 6.4 Combined loss (example)

```text
L_total =
  L_generation
  + w_ctx * L_policy_context
  + w_comp * L_policy_compliance
  + w_ctr * L_policy_contrastive
```

Start with conservative weights, then ramp policy weights after base code generation stabilizes.

---

## 7. Curriculum schedule

Recommended ordering:

1. Phase A: general code generation only.
2. Phase B: context classification (internal vs boundary).
3. Phase C: compliance classification.
4. Phase D: contrastive policy enforcement.
5. Phase E: full multi-task joint tuning.

This avoids destabilizing early learning with strict policy penalties before the model has strong language competence.

## 8. Inference behavior

### 8.1 Policy-aware decoding hints

At generation time, derive context from prompt and retrieved ontology facts:

- If target is `GenServer.handle_*` internal logic, discourage blanket rescue patterns.
- If target is boundary code (controller/input parser/external adapter), encourage explicit error handling.

### 8.2 Generate-check-repair integration

After generation:

1. Run policy checker (AST rules).
2. If non-compliant, run repair prompt with explicit policy constraint.
3. Re-run quality/security checks.

This aligns with your existing generate-check-repair architecture.

## 9. Evaluation for policy learning

Add policy-specific metrics to standard pass@k metrics.

### 9.1 Core metrics

- `internal_over_defensive_rate`:
  - Percent of supervised internal outputs using broad rescue/catch without justification.
- `boundary_under_handling_rate`:
  - Percent of boundary outputs missing expected error handling.
- `policy_compliance_f1`:
  - F1 of policy compliance classifier on held-out annotated set.
- `restart_correctness`:
  - In supervised test harnesses, failing worker restarts according to declared supervisor strategy.

### 9.2 OTP benchmark scenarios

- GenServer callback with invariant violation:
  - Expected: crash + supervised restart behavior.
- Controller/input boundary with malformed payload:
  - Expected: explicit error return path, no opaque crash.

### 9.3 Safety metric

- `silent_failure_rate`:
  - Rate of swallowed exceptions that mask state corruption.
  - Must be near zero.

## 10. Example policy-aligned patterns

### 10.1 Supervised internal callback (acceptable crash posture)

```elixir
def handle_call({:transition, event}, _from, state) do
  # Invariant failures should surface; supervisor handles restart policy.
  new_state = Domain.apply_transition!(state, event)
  {:reply, {:ok, new_state}, new_state}
end
```

### 10.2 Boundary handling (expected failures handled explicitly)

```elixir
def create_user(params) do
  with {:ok, attrs} <- validate_params(params),
       {:ok, user} <- Accounts.create_user(attrs) do
    {:ok, user}
  else
    {:error, reason} -> {:error, reason}
  end
end
```

## 12. Common failure modes and mitigations

- **Failure mode**: model learns "never rescue" globally.
  - Mitigation: strong boundary-labeled data and explicit boundary examples.

- **Failure mode**: model keeps adding blanket rescue in OTP callbacks.
  - Mitigation: increase contrastive weight and targeted negatives.

- **Failure mode**: model swallows exceptions with generic `{:error, :unknown}`.
  - Mitigation: add non-compliance label `swallowed_exception` and penalize in compliance head.

## Conclusion

To make the model reliably OTP-idiomatic, encode supervision failure philosophy as a first-class policy task. The critical design is context separation:

- supervised internals: do not hide invariant failures,
- boundaries: handle expected failures explicitly.

With explicit labels, ontology grounding, multi-task policy heads, and contrastive training, the model can learn when crashing is correct and when defensive handling is required.
